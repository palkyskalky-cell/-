# Архитектура сервиса прогнозирования дефолта по кредитным картам

## 1. Выбор архитектуры: Монолит

Для данного проекта выбран **монолитный подход**. Обоснование:

### Преимущества монолита для этого кейса:
- **Простота разработки и деплоя** — один код, один сервис
- **Низкая задержка** — нет сетевых вызовов между сервисами
- **Легкость тестирования** — можно протестировать всё целиком
- **Меньше инфраструктурных затрат** — не нужно оркестрировать микросервисы

### Почему не микросервисы?
- Нагрузка невысокая (прогнозирование в реальном времени)
- Бизнес-логика простая (одна модель, один эндпоинт)
- Нет необходимости в независимом масштабировании компонентов

---

## 2. Брокеры сообщений (RabbitMQ)

В гипотетическом сценарии масштабирования можно использовать RabbitMQ:

### Для чего:
- **Асинхронная обработка** — клиент отправляет запрос, получает ID, результат приходит позже
- **Пакетная обработка** — для больших объемов запросов
- **Логирование** — асинхронная отправка логов в ELK

### Схема работы:Client → API → RabbitMQ (queue) → Worker (ML модель) → Result Queue → Client

5. Бизнес-метрики
Основные метрики для заказчика:
Снижение финансовых потерь от дефолтов

Формула: Сумма кредитов × (1 - Precision)

Цель: снизить потери на 15%

Доля одобренных заявок при том же уровне риска

Если модель точнее, можно одобрять больше клиентов

Цель: увеличить одобрение на 10% при сохранении уровня дефолта

Как рассчитать:
Финансовые потери = Σ (одобренные заявки × средний кредитный лимит × вероятность дефолта)

7. uWSGI + NGINX (для production)
Схема:
Client → NGINX (порт 80/443) → uWSGI (порт 8000) → Flask API
Зачем:
NGINX — обработка статики, балансировка нагрузки, SSL

uWSGI — управление процессами Python, высокая производительность

Пример конфигурации uWSGI:[uwsgi]
module = src.app.api:app
master = true
processes = 4
socket = 0.0.0.0:8000
