# План A/B-тестирования для моделей прогнозирования дефолта

## 1. Постановка задачи

**Цель:** Сравнить две версии модели прогнозирования дефолта:
- **Контрольная группа (v1)** — текущая модель в production
- **Тестовая группа (v2)** — новая модель с улучшенными параметрами

**Гипотеза:** Новая модель v2 показывает более высокий F1-score для класса дефолта, чем текущая модель v1.

---

## 2. Дизайн эксперимента

### Разделение трафика:
- Случайное распределение 50/50
- Используется параметр `?model_version=v1` или `?model_version=v2` в запросе

### Длительность теста:
- **7 дней** (достаточно для сбора статистики)

### Размер выборки:
- Ожидаемый эффект: +5% к F1-score
- Минимально необходимый размер: 5000 запросов на группу

---

## 3. Метрики

### Основная метрика:
**F1-score для класса дефолта**
- Учитывает и Precision, и Recall
- Важен для несбалансированных данных

### Дополнительные метрики:
1. **Precision для класса дефолта**
   - Важен для минимизации ложных срабатываний
   - Банк не хочет отказывать хорошим клиентам

2. **Снижение финансовых потерь**
   - Бизнес-метрика

---

## 4. Статистический анализ

### Тест:
**Двусторонний t-тест** для независимых выборок

### Уровень значимости:
**α = 0.05** (95% доверительный интервал)

### Критерий успеха:
- **p-value < 0.05** — разница статистически значима
- **F1_v2 > F1_v1** — модель v2 лучше

### Доверительные интервалы:
- Строятся с использованием bootstrap (1000 итераций)
- Для каждой метрики вычисляется 95% CI

---

## 5. Процесс принятия решения

### Если p-value < 0.05 и F1_v2 > F1_v1:
→ **Развернуть v2 в production** ✅

### Если p-value < 0.05 и F1_v2 < F1_v1:
→ **Оставить v1** ❌

### Если p-value >= 0.05:
→ **Продлить тест** или признать результаты незначимыми 🔄

Риск	Решение

Изменение поведения клиентов	Тест на исторических данных перед запуском
Технические ошибки	Мониторинг логов и алертинг
